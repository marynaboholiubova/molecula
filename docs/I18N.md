# Internationalization

Internationalization is a core, day-one architectural concern for Molecula
— not a bolt-on. This document distinguishes what is **active** today from
what is **planned**, and separates two concepts that must never be
conflated.

## UI language vs. generated-content language

These are architecturally separate concerns:

- **UI language** — the language of Molecula's own interface (buttons,
  navigation, marketing copy). This is what `src/messages/*.json` and
  `next-intl` routing govern today.
- **Generated-content language** — the language of AI-produced scripts,
  voiceovers, subtitles, and on-screen text _within a user's project_. This
  will get its own locale/dialect/voice-style architecture in a future task
  (e.g. a project could have an English UI while generating a French movie
  with an `fr-CA` voice). **Not implemented yet** — no code assumes these
  are the same value.

## Active locales

Only **English (`en`)** is active. "Active" means: a real,
human-reviewed translation file exists (`src/messages/en.json`) and the
locale is included in `src/i18n/routing.ts`'s `locales` array, so
`/en/...` actually resolves.

## The language catalog (planned, not active)

`src/config/languages.ts` defines the full 50-language catalog Molecula
intends to support, each entry marked `status: "active"` or `"planned"`.
Planned entries have **no translation file** — nothing fabricates English
text into a `uk.json`, `fr.json`, etc. Activating a language means adding a
real, reviewed message catalog for it and adding its code to
`ACTIVE_LOCALES`/`routing.locales` — never flipping a status flag alone.

The 50 planned base languages: English, Ukrainian, Dutch, French, German,
Spanish, Italian, Portuguese, Russian, Polish, Czech, Slovak, Romanian,
Hungarian, Greek, Turkish, Arabic, Persian, Hindi, Chinese (Simplified),
Chinese (Traditional), Japanese, Korean, Swedish, Norwegian, Danish,
Finnish, Icelandic, Estonian, Latvian, Lithuanian, Bulgarian, Croatian,
Serbian, Slovenian, Bosnian, Albanian, Macedonian, Hebrew, Indonesian,
Malay, Vietnamese, Thai, Bengali, Urdu, Tamil, Filipino, Swahili, Catalan,
Georgian.

## Locale → dialect → accent → voice style (future)

The catalog above lists **base languages only** (no region). A future task
will layer region/dialect variants on top for locales where it matters for
generated content and localization, e.g.:

- English: `en-US`, `en-GB`, `en-AU`, `en-CA`, `en-IN`
- Dutch: `nl-NL`, `nl-BE`
- French: `fr-FR`, `fr-BE`, `fr-CA`, `fr-CH`
- Portuguese: `pt-PT`, `pt-BR`
- Spanish: `es-ES`, `es-MX`, `es-AR`, `es-CO`, `es-US`

None of these are active. This structure is documented here so the eventual
implementation doesn't have to guess at scope.

## Routing approach

`next-intl` with **prefix-based routing** (`localePrefix: "always"` in
`src/i18n/routing.ts`), so every locale — including the default — gets an
explicit path prefix (`/en/...`). This is deliberate for long-term
multilingual SEO: as more locales activate, `/uk`, `/nl`, `/fr`, etc. slot
in without a routing-scheme change.

- `src/proxy.ts` runs `next-intl`'s middleware to resolve and redirect to
  the correct locale-prefixed path (Next.js 16 renamed the
  `middleware.ts` convention to `proxy.ts`).
- `src/app/[locale]/layout.tsx` is the root layout (no non-localized
  `app/layout.tsx` exists); a request to `/` is redirected to `/en` by the
  proxy rather than served by a duplicate nonlocalized page.
- `src/i18n/navigation.ts` exports locale-aware `Link`, `redirect`,
  `usePathname`, `useRouter` — components should import navigation
  primitives from here, not `next/link` / `next/navigation` directly, so
  locale prefixing stays automatic.

## RTL strategy

`src/i18n/locale-direction.ts` resolves `ltr`/`rtl` from the language
catalog (Arabic, Persian, Hebrew, Urdu are marked `rtl`) and is applied to
`<html dir="...">` in the root layout, driven by the active `locale` param.
Since only `en` (`ltr`) is active today, RTL is **not visually exercised**,
but the mechanism is real and unit-tested (`locale-direction.test.ts`) so
activating an RTL language later requires no layout rework — just a real
translation file and a routing entry.
